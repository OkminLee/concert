# 합주 사이트 UX 개선 계획

2026-09-16 · 리서치 및 계획 · 구현 전

Linear의 색감과 상태별 보드는 유지한다. 다음 개선은 **목록을 빨리 훑고, 상세를 보고 돌아와도 작업을 잃지 않는 것**에 집중한다. 기능을 더 넣기 전에 현재의 탐색 방해와 입력 손실을 해결한다.

## 현재 화면에서 확인한 문제

운영 사이트를 Chromium으로 읽기 전용 점검했다. 댓글은 브라우저에만 입력하고 제출하지 않았다. 아래는 특정 화면 상태의 관찰이며, 사용자 전체의 행동 통계가 아니다.

| 관찰 | 의미 | 우선순위 |
|---|---|---|
| 390×844 화면에서 첫 곡 상단 약 699px, 온전히 보이는 곡 1개 | 일정과 탐색 도구가 목록보다 큰 공간을 차지함. 일정 유무에 따라 높이는 달라짐 | P1 |
| ‘모집 완료’와 ‘완료 임박’을 동시에 선택하면 0/23곡 | 같은 상태를 두 필터로 제어해 모순된 조합을 만들 수 있음 | P0 |
| 댓글 입력 → 상세 닫기 → 같은 곡 다시 열기에서 입력값 소실 | 쉽게 닫히는 상세창과 초안 보존이 함께 설계되지 않음 | P0 |
| 음악 검색 결과 영역은 최대 높이 380px의 별도 스크롤, 선택 후 아래 입력 폼으로 이동 | 선택한 곡과 확인할 정보가 떨어져 있음. 실제 사용자 혼동 여부는 미검증 | P1 |
| 제목·뮤지션 입력은 placeholder에 의존 | 입력 후 필드의 의미를 다시 확인하기 어려움 | P1 |

카드 바깥 클릭은 최근 배포 후 자동 브라우저 검사에서는 통과했다. 옥민의 실제 데스크톱에서 해결됐는지는 아직 확인되지 않았다. 이 항목을 완료로 간주하지 않는다.

## 참고 사례와 적용 판단

| 출처 | 확인한 원칙 | 합주 사이트 적용 |
|---|---|---|
| [Linear Display options](https://linear.app/docs/display-options) | 그룹·정렬·표시 속성과 보드/목록을 조정하고 개인 설정을 유지 | 데스크톱 보드 유지. 모바일은 간결한 목록. 정렬·레이아웃 기억은 이미 있으므로 신규 기능으로 세지 않음 |
| [Baymard 적용 필터 표시 연구](https://baymard.com/blog/how-to-design-applied-filters) | 적용된 조건을 목록 근처에서 확인하고 개별 해제할 수 있어야 함 | 상태 제어를 하나로 통합. 선택된 악기·내 참여 조건을 표시하고 즉시 해제. 조건 표시가 여러 줄로 커져 곡을 밀어내지 않도록 제한 |
| [W3C 모달 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) | 열 때 내부 포커스, Tab 범위 유지, Escape 닫기, 닫은 뒤 호출 위치로 포커스 복원 | 상세창 열기/닫기와 목록 복귀를 하나의 흐름으로 검증. 바깥 클릭 닫기는 이 제품의 요구이며 W3C의 필수 요구로 해석하지 않음 |
| [GOV.UK Text input](https://design-system.service.gov.uk/components/text-input/) | placeholder는 지속적인 label을 대신할 수 없음 | 곡명·뮤지션·링크·파트 정원에 항상 보이는 이름을 제공 |
| [WCAG 2.2 Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | AA 최소 대상 크기는 예외 조건을 포함해 24×24 CSS px | 주요 모바일 버튼은 제품 목표로 높이 44px 이상. 확인된 닫기 버튼 높이 37px를 그 자체로 WCAG 실패라 부르지 않음 |

Baymard는 전자상거래 연구다. 합주곡 탐색에 같은 원칙이 도움이 될 것이라는 적용 판단이며, 이 앱에서 검증된 효과 수치는 없다. 댓글 초안 보존은 현재 재현된 입력 손실에 대한 직접 해결책이다.

## 1차: 입력 보존과 필터 정합성

### 상세창

- 곡 ID와 현재 사용자별로 댓글 초안을 탭 세션 동안 유지한다. 닫기·Escape·바깥 클릭·데이터 갱신으로 지우지 않는다.
- 댓글 저장이 성공했을 때 초안을 비운다. 저장 실패 시 입력과 오류 안내를 유지한다. 사용자 전환 시 다른 사람의 초안을 표시하지 않는다.
- 상세를 닫으면 기존 검색·필터·스크롤 위치와 호출 카드의 포커스를 유지한다.
- 긴 상세는 제목부터 보이게 연다. 배경 클릭은 닫고, 내부 클릭과 내부에서 시작한 드래그는 닫지 않는다.

### 필터

- 상태는 단일 선택: 전체 / 모집중 전체 / 모집 시작 / 모이는 중 / 완료 임박 / 모집 완료 / 정원 미설정.
- ‘모집중 전체’는 시작·모이는 중·임박의 합집합이다. 다른 상태와 중복 선택할 수 없다.
- ‘내 참여곡’과 ‘빈자리 악기’만 독립 조건으로 둔다. 악기는 한 번에 하나를 선택하는 현재 범위를 유지한다.
- 결과 수는 현재 조건으로 계산한다. 상태 선택지 숫자를 표시한다면 검색·악기·내 참여 조건을 적용하고 상태 조건만 제외한 후보 수로 통일한다.
- 0건일 때 ‘등록된 곡 없음’과 ‘조건에 맞는 곡 없음’을 구분하고 조건 해제를 제공한다.

완료 기준: 닫기 경로별 초안 보존, 저장 실패 후 재시도, 사용자 전환, 데이터 갱신 검증. 모순된 상태 조합 생성 불가. 결과 수와 표시된 곡 수 일치.

## 2차: 첫 화면과 목록 밀도

모바일 기본 구성을 다음처럼 줄인다.

```
합주곡                         + 곡 추가
다음 합주 날짜·시간                 펼치기
[곡·뮤지션 검색                         ]
[상태: 전체 ▾] [빈자리 악기 ▾] [내 참여]
23곡                       정렬·보기 ▾
곡명 · 뮤지션
기타 1 · 드럼 1                완료 임박
──────────────────────────────────────
다음 곡…
```

일정은 날짜·시간 요약과 펼치기를 남긴다. 상세 일정 조율은 바로 접근할 수 있어야 한다. 데스크톱은 보드 그룹과 목록 전환을 유지하고, 모바일의 정렬·보기 설정을 메뉴에 모은다. 빈자리와 상태는 텍스트로 읽히게 하며 색상만으로 구분하지 않는다. 긴 곡명은 보조 정보보다 우선한다.

제안 목표: 390×844 기본 화면에서 첫 곡 시작 320px 이내, 완전한 곡 행 4개 이상. 이는 구현 후 확인할 목표이지 현재 성과가 아니다. 글자 확대·긴 제목에서는 줄 수 목표보다 읽기와 조작을 우선한다. 320px 폭에서 문서 전체 가로 넘침이 없어야 한다.

## 3차: 곡 추가 흐름

흐름을 ‘서비스 검색 → 결과 선택 → 같은 영역에서 정보·정원 확인 → 추가’로 연결한다.

- 선택 후 결과 목록을 선택곡 요약으로 접고 ‘다른 곡 선택’을 제공한다. 입력 폼까지 갑자기 스크롤시키지 않는다.
- 세 서비스 모두 곡명·뮤지션 또는 채널·원본 링크를 확인하게 한다. YouTube 채널명을 뮤지션으로 확정하지 않는다.
- 입력 label, 검색 중·검색 실패·검색 결과 없음·저장 중·저장 실패 상태를 각각 표시한다.
- 실패해도 선택곡과 작성값을 보존한다. 저장 중 중복 제출을 방지한다.
- 기존 동일 원본 링크 중복 방지를 유지한다. 서로 다른 서비스에 있는 같은 곡 자동 판별은 정확도와 범위를 검토하기 전까지 추가하지 않는다.

완료 기준: 격리 데이터에서 세 서비스 검색·선택·정원 수정·추가 완료, 검색 응답 순서 역전, API 실패, 저장 실패, 중복 링크를 검증한다. 추가 성공 후 새 곡을 찾을 수 있게 표시하며 현재 필터 때문에 가려지면 이를 안내한다.

## 구현 단위와 검증

| 단위 | 예상 변경 파일 | 회귀 검사 |
|---|---|---|
| 초안·상세 복귀 | public/app.js | 댓글, 신청·취소, 데이터 갱신, 포커스, 모든 닫기 방식 |
| 상태 통합 | public/app.js, public/index.html, 필요 시 public/discovery.js | 단계 계산, 정원 0, 초과 신청, 검색·내 곡·악기 조합, 목록·내보내기 순서 |
| 목록·상단 배치 | public/index.html, public/discovery.css | 320/390/768/1440px, 보드/목록, 일정 접근, 긴 제목, 확대 |
| 추가 폼 | public/app.js, public/index.html, public/discovery.css | 세 서비스 선택, 오류 복구, 입력 보존, 중복 제출 |

순서: 1차 기능 회귀 → 2차 화면 비교 → 3차 추가 흐름. 기존 keyed diff를 보존하고 목록 전체 재생성을 피한다. 각 단위는 별도 커밋으로 만든다. 현재 계획은 서버/API 교체를 요구하지 않는다.

브라우저 검사는 Chromium·WebKit 데스크톱/모바일과 키보드로 진행한다. 실제 사용자 데스크톱 확인은 엔진 자동화와 별도로 남긴다. 운영 데이터에는 테스트 곡·댓글·신청을 쓰지 않고, 쓰기 검증은 격리 서버와 데이터 사본에서 한다.

실사용 비교 과제는 ‘특정 곡 찾기’, ‘기타 빈자리 곡 찾기’, ‘댓글 작성 중 닫았다 돌아오기’, ‘검색으로 곡 추가하기’ 네 가지다. 전후 완료 여부·시간·잘못 펼친 횟수를 같은 조건에서 비교한다. 현재 사용자 시간 기준선이 없으므로 개선율을 미리 약속하지 않는다.

## 배포와 복원

구현 전 현재 커밋과 변경 파일 사본을 기록한다. 이번 조사 시 기준 커밋은 3dd21a8이다. 정적 파일 변경도 운영에 즉시 노출되므로 별도 작업 사본에서 검증 후 한 묶음으로 적용하고 자산 버전을 갱신한다. 공개 주소에서 배포 파일과 동작을 다시 확인한다.

문제 발생 시 해당 배포 직전의 변경 파일만 복원하고 자산 버전을 갱신한다. data.json·members.json은 복원 대상으로 삼지 않는다. 서버 파일을 바꾸지 않는 단계에서는 서버 재시작도 필요 없다.

이번 산출물은 조사와 적용 계획이다. 운영 UI는 변경하지 않았다.
